[2026-03-18] | DEFAULT_WORKSPACE_BOUNDS z_min=-0.02 caused 95% of 1024 FPS points to land on the flat table surface (Z ∈ [-0.02, 0.006]), leaving only ~50 pts on the hold — robot did the same thing regardless of hold position | Set z_min=0.006 (at the table surface). [2026-03-18] | Pilot model (50 jug eps, z_min=-0.02) ignored the point cloud entirely — same arm motion regardless of hold position or zero-PC input. [2026-03-18] | Tried to create a second FrankaArm in collect_data.py (Terminal 2) and call stop_skill() to park the arm during PC capture — this permanently kills GotoPoseLive's live skill in Terminal 1 because self.initialize stays False after an external skill kill, with no recovery path | NEVER create a second FrankaArm or call stop_skill() from outside the process that owns the live skill. [2026-03-25] | Arrow key handling added to leap_pip_dip_teleop.py keyboard thread did nothing during data collection — collect_data.py owns stdin via tty.setcbreak, so the second thread never received input | Keyboard input during data collection must go through collect_data.py's stdin reader and _handle_key. Arrow keys are escape sequences (\x1b[A/B) — use select() with 0.05s timeout after detecting \x1b to read the remaining 2 bytes as one atomic sequence. cv2.waitKeyEx() (not waitKey() & 0xFF) must be used to pass full arrow key codes through the cv2 path (Linux: up=65362, down=65364, left=65361, right=65363).

[2026-03-25] | Thumb MCP_Flex keyboard offset had no effect on the physical motor despite the offset variable updating — root cause: mcp_flex_post_scale_offset_rad_per_finger[3]=-1.3 pushes allegro[13] to -1.3 rad, which converts to 1.84 rad in LEAP coords, below the hardware clip minimum of 2.67 (sim_min=-0.47 + π). Every small offset was still within the clipped zone. | When adding a keyboard offset to a joint that has a large post-scale offset, check whether the base value already violates angle_safety_clip limits. Fix by initializing thumb_offsets[1]=+0.9 to start just above the clip boundary. Need ~0.83 rad of offset to clear the clip from -1.3 baseline.

[2026-03-26] | Unity HandController.cs already sends 28 values (16 joint angles + 12 thumb quaternions for base/mid/tip bones) but Python was silently stripping the last 12 with `gripper_values[:16]` — the raw thumb bone orientation data was never used | Before adding new retargeting logic, always audit what data the upstream sender is already providing. [2026-03-26] | BeaVR's thumb IK pipeline uses OVR XRHand 3D joint positions directly (26 joints × xyz), while our Unity app uses the older OVRPlugin.HandState.BoneRotations API (local quaternions). Key tunable constants: THUMB_BASE_POS, THUMB_BONE_AXIS, THUMB_BONE_LENS in leap_thumb_ik_test.py.

[2026-04-01] | Gave user `--hold 0` for pinch data collection — this is WRONG. `--hold` is the physical hold identity, not a session counter. `--hold 0` = edge_A. [2026-04-17] | For comparing two trained policies (with- vs without-taxonomy), running `evaluate.py` serially per model is biased: the hold drifts between the full 20-trial runs, and any operator variation within a single run bleeds into only one model. | Always use the PAIRED protocol in `paired_eval.py`: both policies loaded once, order strictly alternates across pairs so each starts first 50% of the time, and both trials of a pair target the same physical hold position. [2026-04-17] | Initial paired_eval design captured ONE point cloud per pair (shared by both trials). In reality, trial 1's hand contact nudges the hold a few mm, so trial 2 would receive a stale PC that no longer matches the scene. | `paired_eval.py` must capture a FRESH point cloud before each individual trial (not once per pair). Prompt the operator to re-align the hold between trials, park the arm, re-scan, log per-trial centroid + point count, then print the centroid drift (mm) between the two PCs at the end of each pair so outlier pairs can be flagged post-hoc.

[2026-04-17] | First paired_eval smoke test ran 2 crimp pairs cleanly, but Ctrl-C at the next batch's "Press Enter" prompt triggered a segfault during hardware teardown (pyrealsense / FrankaArm cleanup), which killed the daemon thread BEFORE `_save_and_analyze` ran — both completed pairs were lost. | In any signal handler that tears down robot hardware, SAVE DATA FIRST in the main thread (synchronous file write), THEN run hardware teardown in a daemon thread with a short `join(timeout=5)`. Never rely on a daemon thread to both (a) teardown hardware and (b) persist data — pyrealsense/Franka teardowns segfault often enough to make this brittle. `paired_eval.py`'s `_save_only()` also writes a `/tmp/paired_session_<ts>.json` fallback if the primary write fails.

[2026-04-17] | Even with save-on-Ctrl-C, a long evaluation run (80+ pairs) means the operator has to stay through the whole thing or lose session-level progress tracking. Also, save-only-at-end means a crash 79 pairs in = 79 pairs lost. | Eval / data-collection scripts with long runs should (1) accept an explicit 'q' quit button at every natural pause point (between pairs / between batches) that saves and exits cleanly — no Ctrl-C required; (2) save INCREMENTALLY after every completed unit, not just at the end, so worst-case loss is one in-progress unit; (3) support `--resume <session.json>` that restores session_id (to overwrite same file), first_model (to preserve alternation parity), per-batch `completed_pairs` counter, and the original planned-batches spec, so the restart is truly seamless.

[2026-04-20] | I assumed the without-taxonomy ablation failed because of classical "mode collapse" (four behaviours averaged into one), and started writing the paper around that claim. Running `generate_novelty_viz.py` falsified it: the W/o model's mean final-step hand pose still separates the four grasp types at 90% of the demonstrator's between-type spread, and its encoder latent already clusters grasp types at kNN=99%. The real difference is that W/o samples with 15–30% higher within-input variance — a precision effect, not a mode-selection effect. | Before writing a paper narrative around a failure mode, run three quantitative checks on trained ablation models: (1) between-class spread of mean predictions (is the model even using the class structure?), (2) per-input sampling variance at fixed scene (is the conditional tightening probability mass?), (3) latent kNN / silhouette (does the unconditional model already separate classes in representation?). If class structure is preserved in (1) + (3) but (2) differs, the conditional is a precision regularizer, not a mode selector — frame the paper that way. Means don't grasp; individual rollouts do.

[2026-05-15] | Set Cartesian-impedance `kz=100 N/m` for the pull-test compliance and the arm sagged ~10 cm during every pull. LEAP hand mass is ~1 kg → ~10 N constant downward gravity load not in Franka's stock gravity model; static deflection = F/k = 10/100 = 0.1 m. The "Z compliance" was 10× too soft to hold the hand up. | Whenever you set an impedance stiffness on a Franka with a non-standard end-effector (LEAP hand, custom gripper, payload), check the gravity load on that axis and set `kz ≥ 10 × F_gravity / acceptable_droop`. For ~5 mm acceptable droop with the LEAP hand, `kz = 2000 N/m` is the minimum. Compliance for "natural flex" is fine on Y (no gravity loading) but NOT on Z. Reach for `--pull-z-bias` (preemptive upward offset) only as a last resort — stiffness is the cleaner fix.

[2026-05-15] | `paired_eval.py`'s `_cleanup()` was only wired to exception paths (`KeyboardInterrupt`, `QuitRequested`, generic `Exception`). On successful session completion the `try` block exited normally → no cleanup → pyrealsense2 + FrankaArm C-extension destructors raced → "terminate called without an active exception" + core dump that hung the terminal. | Any Python script that talks to `pyrealsense2` or `FrankaArm` C extensions MUST call its hardware-teardown function on **all** exit paths, including normal completion. Use `try / except* / else: cleanup()` — the `else` branch runs only when no exception was raised. Save first, teardown second, `os._exit(0)` last. The C++ destructor race is a known frankapy / pyrealsense2 hazard; cleanup-on-normal-exit is the only reliable mitigation.

[2026-05-15] | Default `--batches` example in CLAUDE.md used bash backslash-line-continuation with leading whitespace on each continuation line. Bash preserved the leading spaces inside the joined string, which split the comma-list into separate argv tokens → "unrecognized arguments" error from argparse for everything after the first line. | When a `--flag value` value contains commas/spaces and you want to break it across lines in docs or shell, either (a) write it on one line, or (b) quote the value AND keep the continuation lines at column 0 with no leading whitespace. Never document a multi-line `--batches` command with indented continuation. The single-line form is the safest for copy-paste-into-terminal use.

[2026-05-15] | The session JSON `paired_session_*.json` did NOT record `pull_dist`, so the printed `--resume` command (`python3 paired_eval.py --resume <path>`) silently dropped the pull test on resume — `pull_dist` defaulted to None and no pull happened, breaking the mid-session continuation flow without warning. | Any per-session CLI flag that affects measurement (not just performance) must be recorded in the session JSON and either auto-restored on `--resume` or surfaced explicitly in the printed resume command. Fixed by adding `pull_dist_m`, `pull_stiffness`, `pull_lateral_stiffness`, `pull_z_stiffness`, `pull_z_bias` to the saved payload and printing them in the quit-time resume hint.

[2026-05-15] | Operator pressed `g` ("good") on every single trial of the 80-pair eval because the binary g/b rating was superseded by the ratchet force readout, but the binary field was still being prompted and logged. McNemar's test on the resulting JSON reported "insufficient discordant pairs (n01 + n10 = 0)" — the binary analysis collapsed to zero discriminative power. | When migrating from a binary metric to a continuous one mid-experiment, either (a) drop the binary prompt entirely so the operator isn't tempted to enter uninformative values, or (b) explicitly redefine what g/b means in the new continuous regime (e.g. "good = ratchet ≥ 5 teeth"). Don't leave a degenerate binary field in the data — it pollutes the analysis path even if downstream code ignores it, and reviewers will ask. For this paper the ratchet-force figures (Wilcoxon + Cohen's d + bootstrap CI) cleanly bypass the binary path.
